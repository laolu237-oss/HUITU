# 2026-10-20 人数 tag 代码兜底（v0.3.28）

## 一句话

出图前检查提示词：**确知本图只有一个人、却没有任何人数/独身 tag 时，自动补 `1girl, solo`**
（或 `1boy, solo`；判不出性别只补 `solo`）。这是「规范劝告」之外的最后一道确定性防线。

## 为什么

上一轮实测（v4 之前）四张单人图全部缺 `1girl`/`solo`，被画成 2–3 个同一个人。
把「必须写人数 tag」写进预设属于**劝告**，模型仍会漏；预设也已到 11174 字符（上限 12000），
继续堆文案没有空间。所以改成代码兜底。

## 设计上的三个关键取舍

1. **只有能证明「一个人」才动手**：依据是 `names`（ComfyUI 角色名数组）或 NAI `characters[]`
   长度为 1。拿不到证据一律不补 —— 给双人画面补 `solo` 会把两个人挤成一个，比漏画更糟。
2. **性别判不出来只补 `solo`**：`solo` 本身就是「画面只有一个角色」的 danbooru 语义，安全且有效；
   补错 `1boy` 比不补更坏。性别线索来自 tag 本身 + NAI 的 `characters[].tag`（`hintText`）。
3. **插在触发词之后**：LoRA 触发词要尽量靠前，人数 tag 按规范也该在最前；
   两者同时存在时唯一兼容的顺序是「触发词第一、人数紧跟」。

## 改了什么

- **新增 `src/countTag.ts`**：`ensureSoloTag(tag, { characterCount, triggerToken, hintText })`。
  - 已有人数 tag（`1girl` / `2girls` / `solo` / `no humans` …）原样返回；
  - 幂等，重复调用不叠加；
  - 性别按「词」判定而非正则 `\b`：`1girl` 的 `g` 前是数字，`\b` 不成立会漏判；
    同时避免 `cowgirl`、`bracelet` 这类子串误判。
- **`src/generate.ts`**：NAI 分支与 ComfyUI 分支都在发请求前调用它；
  ComfyUI 简易模式仍先补人数、再 `ensureVerbatimItems` 补齐触发词串。
- **新增 `src/countTag.test.ts`**（12 例）＋ `generate.test.ts` 的 NAI 用例改为断言新行为。

## 怎么验证

```bash
npx vitest run    # 911 passed / 3 skipped
npm run build     # v0.3.28
```

用户侧：跑一楼单人图 → 打开请求历史或卡片编辑器看最终提示词，开头应有 `1girl, solo`。

## 已知边界（重要）

- **只覆盖「有角色名」的路径**：ComfyUI 的 `names` 仅在角色库有条目需要整串/LoRA 时下发；
  纯字段库且未绑 LoRA 的角色，`characterCount` 未知 → 不补。这是刻意的保守。
- **不改写正文里的 tag**：兜底只作用于「发给后端的提示词」，聊天记录里的 `<bbi_image>` 原文不动，
  `promptHash` 因此保持稳定（老图不会无辜变 stale）。代价是编辑器里看不到补的那两个词。
- 若某楼确实是双人但模型漏了 `2girls`，兜底不会介入（`characterCount` = 2）——
  这种情况仍要靠规范里的「人数 tag 必须明确」。

## 回滚

删 `src/countTag.ts` 与其测试，撤掉 `generate.ts` 两处调用，还原 `generate.test.ts` 的断言。
